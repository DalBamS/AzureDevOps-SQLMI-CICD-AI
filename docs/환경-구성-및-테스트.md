# 개발 환경 구성 및 테스트

이 문서는 교육용 최소 구현을 로컬과 Azure DevOps에서 확인하는 절차입니다. 최대 방어
참고본은 [`reference/hardened`](https://github.com/DalBamS/AzureDevOps-SQLMI-CICD-AI/tree/reference/hardened)에
보존되어 있습니다.

## 1. 필수 도구

| 도구 | 용도 |
|---|---|
| .NET 10 SDK | SQL 프로젝트 빌드, SqlPackage 설치 |
| PowerShell 7 | `eng/*.ps1` 실행 |
| Docker | 선택적 SQL Server 2025 통합 테스트와 실습 랩 |
| SqlServer PowerShell module | managed GO parser와 `ValidatedScript` 실행 |
| Azure CLI | SQL MI/Foundry Entra token |

파이프라인의 `sqlPackageVersion`과 `sqlServerModuleVersion` 변수가 도구 버전의 단일
기준입니다. 작업에는 `SQLSERVER_MODULE_VERSION` 환경 변수로 전달됩니다.

## 2. 빌드 엄격도

```powershell
pwsh ./eng/Build.ps1 -Strictness Lenient
pwsh ./eng/Build.ps1 -Strictness Strict
```

`BuildStrictness`는 `Lenient|Strict`만 지원합니다. SQL 프로젝트만으로 "신규 또는 변경
오브젝트의 warning만 error"를 안정적으로 구분하기 어렵습니다. 도입 시 Lenient CI의 전체
warning 수를 기록하고, 팀이 정한 임계값을 릴리스마다 낮춰 0에 도달한 뒤 Strict를
필수화하십시오. warning 번호별 suppress를 중간 모드로 숨기지 않습니다.

## 3. Update policy와 collation

현재 SQL 프로젝트 DSP와 컨테이너 기준은 SQL Server 2025입니다. Microsoft Learn은 기존과
신규 SQL MI의 기본 update policy를 SQL Server 2022로 설명합니다. 한편 공식 What's new는
2026년 3월 SQL Server 2025 update policy GA를 공지하며, Learn은 시스템 기본값이 바뀔 수
있으므로 의도를 명시하라고 경고합니다. 이는 2025가 현재 기본이라는 뜻은 아닙니다.
배포 전에 Azure Portal에서 실제 선택값과 적용 상태를 확인하십시오. 2022에서 2025로
올린 database format은 되돌릴 수 없습니다.

- [SQL MI update policy](https://learn.microsoft.com/azure/azure-sql/managed-instance/update-policy)
- [SQL MI What's new](https://learn.microsoft.com/azure/azure-sql/managed-instance/doc-changes-updates-release-notes-whats-new)
- [SQL MI 생성 quickstart](https://learn.microsoft.com/azure/azure-sql/managed-instance/instance-create-quickstart)

교육 환경의 대표 collation은 `Korean_Wansung_CI_AS`와
`SQL_Latin1_General_CP1_CI_AS`입니다. 서로 다른 collation의 문자열 비교/조인은
collation conflict 오류를 만들 수 있습니다. 필요한 경계에서 명시적 `COLLATE`를 사용하고
인덱스 및 비교 의미를 함께 검토하십시오. SQL MI instance collation은 생성 후 변경할 수
없으므로 생성 전에 결정합니다. `ModelCollation`은 실제 DB collation을 설정하지 않습니다.

## 4. 로컬 검증

```powershell
pwsh ./eng/Build.ps1
pwsh ./eng/Test-SqlPolicy.ps1
pwsh ./eng/Test-Phase2.ps1
pwsh ./eng/Test-FailureLabs.ps1
pwsh ./eng/Test-Database.ps1
```

`Test-Database.ps1`은 SQL Server 2025 컨테이너를 시작하고 DACPAC을 Publish한 뒤
`tests/integration/*.sql`을 실행합니다. Docker가 없는 환경에서는 앞의 네 정적/오프라인
검사만 실행합니다.

## 5. 정책 검사의 의도적 한계

`SqlCmd.Common.psm1`은 GO 분리를
`Microsoft.SqlTools.ManagedBatchParser`에 전적으로 위임합니다. 저장소는 새 SQL
lexer/tokenizer/state machine을 구현하지 않습니다.

`Test-DeploymentScript.ps1`과 인스턴스 스크립트 검사는 batch text 정규식 수준입니다.
주석·문자열·quoted identifier 안의 단어를 오탐하거나, 복잡한 동적 SQL/비정형 표기를
놓칠 수 있습니다. 이를 코드 예외로 보완하지 않습니다. 생성된 `deploy.sql`과
`database/instance`의 소수 스크립트는 DBA가 사람 review해야 합니다.

`DROP INDEX`/`DROP CONSTRAINT`는 기본 warning이며 같은 script에서 동일 object name의
대응 `CREATE`/`ADD`가 없으면 error입니다. `sp_rename`과 `SET NOEXEC`는 warning,
검토할 수 없는 동적 실행은 error입니다. allowlist는 티켓과 만료일이 있는 한시적 예외만
허용합니다.

## 6. 실제 SQL MI 확인 항목

로컬 검증은 SQL MI의 VNet/DNS, WIF, Portal update policy, Environment 승인,
PITR retention, Foundry 배포 및 실제 collation을 검증하지 않습니다. 강의 전에 대상
구독에서 별도로 리허설하십시오.
