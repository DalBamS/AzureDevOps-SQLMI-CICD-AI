# 개발 환경 구성 및 테스트

이 문서는 교육용 최소 구현을 로컬과 Azure DevOps에서 확인하는 절차입니다. 최대 방어
참고본은 [`reference/hardened`](https://github.com/DalBamS/AzureDevOps-SQLMI-CICD-AI/tree/reference/hardened)에
보존되어 있습니다.

## 1. 저장소 구조

```text
.
├─ database/App.Database/          SDK-style SQL 프로젝트
│  ├─ Schemas/                     사용자 스키마
│  ├─ Tables/                      테이블 및 확장 속성 메타데이터
│  ├─ Views/                       뷰
│  ├─ StoredProcedures/            저장 프로시저
│  └─ Scripts/                     빌드 모델에서 제외되는 배포 후 스크립트
├─ database/instance/              멱등 SQL MI 로그인·SQL Agent job 스크립트
├─ tests/integration/              DACPAC 배포 후 실행하는 SQL 스모크 테스트
├─ tests/fixtures/                 오프라인 회귀 테스트용 고정 입력
├─ labs/                           의도적 실패 실습용 SQL, report, allowlist
├─ docs/                           설정·테스트·랩·롤백 문서
├─ eng/                            빌드, 정책, 컨테이너 테스트, 배포, BACPAC 도구
│  └─ policy/                      배포 스크립트 게이트 allowlist
├─ pipelines/profiles/             연결 정보 없는 환경별 DAC publish profile
├─ pipelines/templates/            환경 배포 stage 템플릿
├─ pipelines/drift-report.yml      읽기 전용 정기 드리프트 리포트
├─ ai/                             AI 데이터베이스 변경 리뷰 지침
├─ NuGet.config                    재현 가능한 Microsoft.Build.Sql 복원 소스
└─ azure-pipelines.yml             CI/CD 진입점
```

## 2. 필수 도구

| 도구 | 용도 |
|---|---|
| .NET 10 SDK | SQL 프로젝트 빌드, SqlPackage 설치 |
| PowerShell 7 | `eng/*.ps1` 실행 |
| Docker | 선택적 SQL Server 2025 통합 테스트와 실습 랩 |
| SqlServer PowerShell module | managed GO parser와 `ValidatedScript` 실행 |
| Azure CLI | SQL MI/Foundry Entra token |

파이프라인의 `sqlPackageVersion`과 `sqlServerModuleVersion` 변수가 도구 버전의 단일
기준입니다. 작업에는 `SQLSERVER_MODULE_VERSION` 환경 변수로 전달됩니다.

## 3. Azure DevOps 중심 테스트

### 3.1 선택적 로컬 정적 빌드

```powershell
pwsh ./eng/Build.ps1
pwsh ./eng/Build.ps1 -Strictness Lenient
pwsh ./eng/Build.ps1 -Strictness Strict
```

결과:

```text
artifacts/dacpac/App.Database.dacpac
```

빌드는 다음 항목을 검사합니다.

- SQL Server 2025/SQL MI 대상 플랫폼(`Sql170DatabaseSchemaProvider`) 모델 유효성
- SQL 참조 및 구문
- Microsoft.Build.Sql 코드 분석
- 선택한 `BuildStrictness`의 T-SQL warning 정책(기본 `Strict`)

엄격도 단계와 도입 순서는 §4를, 대상 플랫폼 선택 기준은 §5를 참고하십시오.

빌드 외 오프라인 검증은 다음과 같습니다. Docker가 없는 환경에서는 마지막 명령을
생략합니다.

```powershell
pwsh ./eng/Test-SqlPolicy.ps1        # 3.2
pwsh ./eng/Test-Phase2.ps1           # 정책 게이트·드리프트 감지·배포 모드 자체 검사
pwsh ./eng/Test-FailureLabs.ps1      # Lab B~D 오프라인 차단 재현
pwsh ./eng/Test-Database.ps1         # 3.3, Docker 필요
```

### 3.2 선택적 로컬 SQL 정책 검사

```powershell
pwsh ./eng/Test-SqlPolicy.ps1
```

`artifacts/sql-policy-report.md`를 생성합니다. Seed를 포함한 모든 SQL 소스에서
`DELETE`, `TRUNCATE`, 비멱등 배포 스크립트를 오류로 검사하고 `SELECT *`, `NOLOCK`은
경고로 기록합니다.

이 검사는 **소스 lint**입니다. 상태 기반 프로젝트의 소스에는 `DROP`이 존재하지 않고
파괴 DDL은 DacFx가 생성한 `deploy.sql`에만 나타나므로, 실제 파괴 DDL 차단은
`eng/Test-DeploymentScript.ps1`이 담당합니다. 두 검사의 역할을 혼동하지 마십시오.

### 3.3 PR 통합 테스트

SQL 변경 브랜치를 push합니다.

```powershell
git push --set-upstream origin <branch-name>
```

GitHub에서 `main` 대상 PR을 생성하면 Azure DevOps의 `IntegrationTest` job이
Microsoft-hosted `ubuntu-latest` agent에서 `eng/Test-Database.ps1`을 실행합니다.

1. 빌드된 DACPAC artifact 다운로드
2. NuGet tool package `Microsoft.SqlPackage` 설치
3. 임시 SQL Server 2025 컨테이너 시작 후 컨테이너 내부의 실제 `sqlcmd` 경로 탐색
4. DACPAC Publish
5. `tests/integration/*.sql`을 파일명 순서대로 실행
6. 임시 컨테이너와 암호 제거

컨테이너는 Azure DevOps agent 안에서만 사용하므로 개발 PC에 Docker Desktop을 설치할
필요가 없습니다. `Test-Database.ps1`은 파이프라인 재현과 agent 장애 조사용 내부
명령으로도 유지합니다.

통합 테스트 작성 규약은 [tests/README.md](../tests/README.md)를 참고하십시오.

### 3.4 AI SQL 리뷰

AI 리뷰는 결정론적 정책 검사를 대체하지 않고 SQL 변경의 설계 및 배포 위험을 보강합니다.
PR에서는 SQL diff를 검토해 GitHub 코멘트와 pipeline artifact를 생성하고, 환경 배포
전에는 실제 `deploy.sql`을 다시 검토합니다. Azure Pipelines의 Workload Identity
Federation과 Entra ID 인증을 사용하므로 API key를 저장하지 않습니다.

입력이 `MaxInputCharacters`(기본 120000)를 넘으면 여러 청크로 나누어 순차 호출하고
결과를 병합합니다. risk는 `low < medium < high`의 최댓값입니다. 응답이
`risk`, `summary`, `blockingFindings`, `advisories` 계약을 만족하지 않으면 실패합니다.

네트워크 없이 파싱·병합 동작만 확인하려면 고정 응답 파일을 사용합니다.

```powershell
pwsh ./eng/Invoke-AiDatabaseReview.ps1 `
  -ReviewInputPath ./tests/fixtures/deployment-safe.sql `
  -ValidateOnlyResponsePath ./tests/fixtures/ai-review-single.json `
  -OutputPath ./artifacts/ai-review/offline.json
```

AI 결과는 기본적으로 advisory입니다. blocking으로 승격하는 조건은
[Azure DevOps 설정 — advisory에서 blocking으로 승격하는 기준](Azure-DevOps-설정.md#112-advisory에서-blocking으로-승격하는-기준)을
참고하십시오.

### 3.5 실제 SQL MI 환경 배포

PR 검증과 병합이 끝나면 Azure DevOps에서 파이프라인을 수동 실행합니다.

| Parameter | 결과 |
|---|---|
| `deployDev=true` | `AppDb_CicdDemo_Dev` 배포 및 SQL MI 스모크 테스트 |
| `deployTest=true` | Test 승인 후 `AppDb_CicdDemo_Stg` 배포 및 테스트 |
| `deployProd=true` | Prod 승인 후 `AppDb_CicdDemo_Live` 배포 및 테스트 |
| `deploymentMode=Publish` | 기본. `ValidatedScript`는 명시할 때만 사용 |
| `maxParallel=4` | 카나리 통과 뒤 나머지 DB의 최대 동시 배포 수 |
| `validateAllDatabasePlans=false` | 대표 DB만 계획; `true`이면 모든 DB DeployReport 생성 |
| `databasePlanDriftPolicy=Warn` | 전수 계획 차이를 경고 또는 `Fail`로 차단 |
| `deployInstanceObjects=false` | DB fan-out 성공 후 인스턴스 오브젝트 job 실행 |

#### 대상 데이터베이스와 카나리

Variable group의 `databaseNames`에 쉼표 구분 목록을 지정합니다. 값이 없거나 변수가
정의되지 않았으면 기존 `databaseName` 단일 값을 사용합니다. 목록 첫 항목이 Plan의 대표
DB이자 카나리이며, 카나리 배포와 `Test-DeployedDatabase.ps1`이 성공해야 나머지 fan-out이
시작됩니다. 모든 DB의 결과를 수집한 뒤 하나라도 실패하면 stage가 실패하고 실패 목록과
성공/실패 수가 Azure DevOps summary에 게시됩니다.

fan-out 직전에 Azure SQL token을 한 번 발급해 worker에 전달합니다. token은 롤아웃 중
갱신되지 않으므로, 대상이 많고 DDL이 길면 후반부에서 인증 오류가 발생할 수 있습니다.

#### 계획과 승인 검증

기본 계획은 대표 DB 하나만 조회하므로 비용이 낮습니다. `validateAllDatabasePlans=true`는
각 DB의 DeployReport를 artifact에 추가하고 대표 계획과 비교합니다. 차이는 `Warn`이면
승인자에게 경고하고 DB별 보고서를 승인 기준으로 보존하며, `Fail`이면 Plan을 중단합니다.

배포 직전에는 각 DB의 DeployReport를 같은 profile로 다시 생성해 승인본과 비교합니다.
기본 대표 전용 모드는 각 DB의 작업 집합을 승인된 대표 보고서와 비교하고, 전수 모드는
각 DB의 현재 보고서를 해당 DB의 승인 보고서와 비교합니다. 비교가 실패하면 배포하지
않고 재계획·재승인을 요구합니다.

기본 `Publish` 모드는 검증을 통과한 뒤 `/Action:Publish`를 실행하며, DacFx가 실행
시점에 계획을 다시 계산합니다. `ValidatedScript` 모드는 승인된 Script 원문을
`Invoke-Sqlcmd`로 실행해 승인본과 실행본을 완전히 일치시키는 대신, 다중 DB에서는
`validateAllDatabasePlans=true`를 요구합니다. 두 모드의 트레이드오프는
[Azure DevOps 설정 — 승인 게이트와 배포 모드](Azure-DevOps-설정.md#7-승인-게이트와-배포-모드)에
정리했습니다.

#### 실행 제한 시간

SqlPackage의 `CommandTimeout` 기본값은 60초입니다. 장기 MI DDL에는 부족하므로 profile은
3600초를 명시하며 파이프라인 `sqlCommandTimeout` parameter로만 재정의합니다. 연결 수립
제한인 connection string의 `Connection Timeout=30`과 혼동하지 마십시오.

#### 정기 드리프트 리포트

`pipelines/drift-report.yml`은 매일 02:00 UTC에 Dev/Test/Prod를 점검합니다. 각 환경의
대표 DB 하나만 조회해 비용을 환경당 DeployReport 1회로 제한합니다. 변경이 없으면
성공하고, 변경이 있으면 환경별 artifact를 게시하며 `SucceededWithIssues`로 표시합니다.
인증, 네트워크, SqlPackage, XML 오류는 경고로 바꾸지 않고 실패합니다. 이 파이프라인은
`/Action:DeployReport`만 실행합니다.
파이프라인은 환경별로 `eng/New-DatabaseDriftReport.ps1`을 호출하며, 이 스크립트는
읽기 전용 액션만 수행합니다.

#### 배포 스크립트 게이트

`Plan*` stage는 `deploy.sql` 생성 직후 결정론적 게이트를 실행합니다. 오류가 하나라도
있으면 stage를 실패시키고, 경고·오류·allowlist 적용 결과를 `deployment-script-policy.md`로
게시합니다. 탐지 범위와 severity는 §8에 정리했습니다. AI 검토와 사람 승인은 이 게이트를
대체하거나 우회하지 않습니다.

예외가 필요한 경우 `eng/policy/deploy-allowlist.json`에 다음 필드를 추가합니다.

```json
[
  {
    "rule": "DEPLOY001",
    "pattern": "\\[dbo\\]\\.\\[ApprovedLegacyTable\\]",
    "ticket": "CHG-1234",
    "expiresOn": "2026-08-31"
  }
]
```

`pattern`은 탐지된 statement에 적용되는 정규식입니다. 만료일이 지난 항목은 자동으로
무효가 되며 보고서의 expired 항목에 남습니다. 티켓과 만료일 없는 영구 예외는 두지
않습니다.

### 3.6 인스턴스 오브젝트와 재시도

DACPAC은 데이터베이스 범위입니다. SQL Agent job, 로그인, 링크드 서버, DB Mail 같은
인스턴스 수준 오브젝트는 포함되지 않으므로 별도 경로로 배포합니다.

`database/instance`의 `001-entra-login.sql`, `010-agent-job.sql`은 SQLCMD 변수로 실제
이름을 주입하며 존재 여부에 따라 생성/갱신합니다. `deployInstanceObjects=true`일 때만
database fan-out 성공 후 별도 job에서 실행됩니다. Variable group에는
`instanceEntraLoginName`, `instanceAgentJobName`, `instanceAgentJobOwner`를 설정합니다.

작성 규칙:

- 파일명은 `NNN-description.sql` 형식이며 이름 순서대로 실행됩니다
- 첫 줄에 `-- Idempotency:` 선언으로 재실행 시 동작을 명시합니다
- 모든 변경은 `IF EXISTS` 또는 `IF NOT EXISTS` 존재 검사 안에서 수행합니다
- `DROP`, `TRUNCATE`, `GRANT`, `DENY`, `REVOKE`와 동적 SQL은 게이트가 차단합니다
- 파일이 참조하는 SQLCMD 변수 집합과 전달 변수 집합이 정확히 같아야 합니다

로컬 사전 확인:

```powershell
pwsh ./eng/Deploy-InstanceObjects.ps1 `
  -ServerName '<sql-mi-fqdn>' `
  -AccessToken '<access-token>' `
  -SqlcmdVariables @{
    EntraLoginName = '<entra-login-name>'
    AgentJobName = '<agent-job-name>'
    AgentJobOwner = '<job-owner-login>'
  } `
  -WhatIf
```

스크립트는 Azure CLI가 반환한 문자열 access token을 `Invoke-Sqlcmd -AccessToken`에
직접 전달합니다. 현재 SqlServer module은 이 parameter에 문자열과 `SecureString`을 모두
허용합니다.

- [`Invoke-Sqlcmd -AccessToken`](https://learn.microsoft.com/powershell/module/sqlserver/invoke-sqlcmd#-accesstoken)

인스턴스 스크립트 검사는 정규식 수준입니다. 파일 수가 적고 사람이 검토하는 것을
전제하므로 정적 분석을 강화하는 대신 리뷰를 필수로 둡니다. 한계는 §8을 참고하십시오.

배포가 실패했을 때의 재시도와 복구는 [롤백 런북](롤백-런북.md)을 따릅니다.

### 3.7 반복 테스트와 초기화

데모 데이터베이스 최초 구성은 `eng/Initialize-DemoDatabases.ps1`로 수행합니다. 절차는
[Azure DevOps 설정 — Demo 데이터베이스 최초 구성](Azure-DevOps-설정.md#63-demo-데이터베이스-최초-구성)을
참고하십시오.

테스트 브랜치를 push해도 `main` 내용은 변경되지 않습니다. `main`은 PR을 merge했을 때만
변경됩니다. 반복 테스트는 매번 최신 `main`에서 새 브랜치를 만듭니다.

```powershell
$testBranch = 'demo/sql-change-01'

git switch main
git pull --ff-only origin main
git switch -c $testBranch

# database/App.Database 및 필요한 tests/integration 파일 수정
git add ./database/App.Database ./tests/integration
git commit -m "Test database change"
git push --set-upstream origin $testBranch
```

테스트만 수행하는 PR은 merge하지 않고 닫습니다. 테스트 종료 후 브랜치와 로컬 생성물을
다음 순서로 정리합니다.

```powershell
$testBranch = 'demo/sql-change-01'

git switch main
git pull --ff-only origin main

# 테스트 브랜치의 commit을 더 이상 보관하지 않을 때만 실행
git branch -D $testBranch
git push origin --delete $testBranch

pwsh ./eng/Clear-GeneratedArtifacts.ps1
git status
```

`Clear-GeneratedArtifacts.ps1`은 `artifacts`, `TestResults`, `bin`, `obj`만 삭제합니다.
`App.Database.sqlproj`와 SQL 소스는 삭제하지 않습니다. 테스트 브랜치에 commit하지 않은
변경이 남아 있으면 먼저 보관하거나 다음 명령으로 명시적으로 폐기한 후 `main`으로
전환합니다.

```powershell
# 아래 두 명령은 해당 경로의 미커밋 변경과 새 파일을 영구 삭제합니다.
git restore --staged --worktree -- ./database/App.Database ./tests/integration
git clean -nd -- ./database/App.Database ./tests/integration
git clean -fd -- ./database/App.Database ./tests/integration
```

테스트 PR을 이미 merge했다면 `main`을 강제로 이전 commit으로 reset하거나 force-push하지
않습니다. 별도 브랜치에서 merge commit을 되돌리는 PR을 만듭니다.

```powershell
git switch main
git pull --ff-only origin main
git switch -c revert/demo-sql-change
git revert <merge-commit-sha>
git push --set-upstream origin revert/demo-sql-change
```

Demo SQL MI도 배포 전의 빈 상태로 되돌리려면 먼저 대상 확인만 수행합니다.

```powershell
$resourceGroup = '<sql-mi-resource-group>'
$managedInstance = '<sql-mi-name>'
$sqlServer = '<sql-mi-public-fqdn>'
$deployerPrincipal = '<deployer-principal-name>'

az sql mi start -g $resourceGroup --mi $managedInstance
$token = az account get-access-token `
  --resource 'https://database.windows.net/' `
  --query accessToken `
  --output tsv

& ./eng/Reset-DemoDatabases.ps1 `
  -ServerName $sqlServer `
  -Port 3342 `
  -DatabaseName @('AppDb_CicdDemo_Dev', 'AppDb_CicdDemo_Stg', 'AppDb_CicdDemo_Live') `
  -DeployerPrincipalName $deployerPrincipal `
  -AccessToken $token `
  -ConfirmReset `
  -WhatIf
```

출력된 세 데이터베이스가 정확한 경우 `-WhatIf`만 제거해 실행합니다. 이 작업은
`AppDb_CicdDemo_*` 데이터와 스키마를 영구 삭제하고 빈 DB와 배포 계정 권한만
재생성합니다. 이후 `main` 기준 Azure DevOps 배포를 실행하면 최초 Demo 상태가 다시
구성됩니다. 실제 운영 DB에는 이 스크립트를 사용하지 않습니다.

Azure DevOps 실행 기록과 artifact는 감사 이력이므로 다음 테스트에 영향을 주지 않으며
초기화 과정에서 삭제하지 않습니다.

## 4. 빌드 엄격도

`BuildStrictness`는 `Lenient|Strict` 두 단계만 지원합니다.

| 모드 | 코드 분석 | warning-as-error |
|---|---|---|
| `Lenient` | 실행 | 아니요(경고 수집) |
| `Strict` | 실행 | 예 |

SQL 프로젝트만으로 "신규 또는 변경 오브젝트의 warning만 error"를 안정적으로 구분하기
어렵기 때문에 중간 단계를 두지 않았습니다. 기존 데이터베이스를 이 방식으로 옮길 때는
Lenient CI의 전체 warning 수를 기록하고, 팀이 정한 임계값을 릴리스마다 낮춘 뒤 0에
도달하면 Strict를 필수화하십시오. warning 번호별 suppress로 중간 상태를 숨기지
않습니다.

## 5. Update policy와 collation

현재 SQL 프로젝트 DSP와 컨테이너 기준은 SQL Server 2025입니다.

| SQL MI update policy | SQL 프로젝트 DSP | 검증 컨테이너 |
|---|---|---|
| SQL Server 2022 | `Sql160DatabaseSchemaProvider` | `2022-latest` |
| SQL Server 2025 | `Sql170DatabaseSchemaProvider` | `2025-latest` (현재 기준선) |
| Always-up-to-date | `Sql170DatabaseSchemaProvider` 이상 | `2025-latest`를 최소 기준으로 사용 |

기본값 표기는 문서마다 다릅니다. Microsoft Learn의 update policy 문서는 기존 및 신규
SQL MI의 기본 정책을 SQL Server 2022로 설명하는 반면, What's new는 2026년 3월 SQL Server
2025 update policy GA를 공지하며 시스템 기본값이 바뀔 수 있으므로 의도를 명시하라고
안내합니다. **어느 쪽도 단정하지 말고 배포 전에 Azure Portal에서 실제 선택값과 적용
상태를 확인하십시오.** 인스턴스를 만들 때 update policy를 명시적으로 지정하고 서비스
기본값에 의존하지 않는 것이 안전합니다.

SQL Server 2022 update policy는 SQL Server 2022 mainstream support 종료일인
**2028-01-11**까지 제공된다고 문서화되어 있습니다. 2022에서 2025로 올린 database
format은 되돌릴 수 없으므로 전환 전에 DSP, 컨테이너, 복원 및 MI Link 요구사항을 함께
재검증합니다.

- [SQL MI update policy](https://learn.microsoft.com/azure/azure-sql/managed-instance/update-policy)
- [SQL MI What's new](https://learn.microsoft.com/azure/azure-sql/managed-instance/doc-changes-updates-release-notes-whats-new)
- [SQL 프로젝트 target platform과 DSP](https://learn.microsoft.com/sql/tools/sql-database-projects/concepts/target-platform)

교육 환경의 대표 collation은 `Korean_Wansung_CI_AS`와 `SQL_Latin1_General_CP1_CI_AS`
입니다. 서로 다른 collation의 문자열 비교/조인은 collation conflict 오류를 만들 수
있습니다. 필요한 경계에서 명시적 `COLLATE`를 사용하고 인덱스 및 비교 의미를 함께
검토하십시오.

**SQL MI instance collation은 생성 후 변경할 수 없으므로 인스턴스를 만들기 전에
결정해야 합니다.** `.sqlproj`의 `ModelCollation`은 빌드 모델 비교 동작이며 실제 대상
데이터베이스 collation을 설정하거나 보장하지 않습니다. profile의
`ScriptDatabaseOptions=False`이므로 배포가 collation 변경을 시도하지도 않습니다. 대상
생성 시점과 배포 전 점검에서 별도로 확인해야 합니다.

## 6. 데이터베이스 프로젝트 확장 규칙

### 스키마 오브젝트

- 선언적 최종 상태는 `database/App.Database` 아래 오브젝트 종류별 폴더에 저장합니다.
- 한 파일에 주 데이터베이스 오브젝트 하나를 둡니다.
- 테이블/컬럼 설명은 `MS_Description` 확장 속성으로 함께 버전 관리합니다.
- 환경별 서버명, 사용자명, 암호를 SQL 프로젝트에 넣지 않습니다.
- 사용자, 로그인, 권한, database/server role membership은 publish profile에서 제외합니다.
  DACPAC 밖의 승인된 보안 IaC 또는 DBA 절차로 관리하고 별도 감사 이력을 남깁니다.

### 정적 데이터

- 작은 참조 데이터만 `Scripts/Seed`에 둡니다.
- 모든 스크립트는 재실행 가능한 idempotent 형태여야 합니다.
- `usp_SeedFeatureFlags`처럼 seed 실행 진입점을 하나로 두고 통합 테스트에서 두 번 호출해
  행 수가 변하지 않는지 검증합니다.
- 대량 데이터 이동은 BACPAC 또는 별도 ETL/마이그레이션 작업으로 분리합니다.

### 위험한 변경

컬럼 제거, 타입 축소, 대형 테이블의 NOT NULL 변경은 한 번에 수행하지 않습니다.

1. Expand: 신규 컬럼/오브젝트 추가
2. Migrate: 데이터 백필 및 이중 쓰기
3. Contract: 소비 코드 전환 확인 후 구 오브젝트 제거

`BlockOnPossibleDataLoss=True`와 배포 스크립트 게이트는 최후 방어선이지 마이그레이션
설계를 대신하지 않습니다. `AllowIncompatiblePlatform`은 사용하지 않으므로 DSP와 SQL MI
update policy가 맞지 않으면 배포를 중단합니다.

## 7. BACPAC 사용

BACPAC은 논리적 데이터 이동과 시딩 수단입니다. 스키마 배포는 DACPAC이 담당하며 BACPAC을
일반적인 롤백 수단으로 사용하지 않습니다.

SqlPackage를 설치하고 Azure CLI로 로그인한 뒤 실행합니다.

```powershell
dotnet tool install --global Microsoft.SqlPackage --allow-roll-forward
az login

pwsh ./eng/Export-Bacpac.ps1 `
  -ServerName '<sql-mi-public-fqdn>' `
  -Port 3342 `
  -DatabaseName 'AppDb' `
  -OutputPath './artifacts/backup/AppDb.bacpac'

pwsh ./eng/Import-Bacpac.ps1 `
  -ServerName '<target-mi-public-fqdn>' `
  -Port 3342 `
  -DatabaseName 'AppDb_Seeded' `
  -BacpacPath './artifacts/backup/AppDb.bacpac'
```

BACPAC에는 데이터가 포함될 수 있으므로 Git에 커밋하지 않습니다. 민감 데이터는 Test 환경
반입 전에 마스킹하고, 운영 export는 일관된 복사본이나 업무 정지 구간에서 수행합니다.

포트는 사용하는 endpoint에 따라 다릅니다. VNet-local endpoint와 private endpoint는
1433이므로 `-Port`를 생략할 수 있고, public endpoint는 3342를 지정합니다. 세 endpoint의
차이는 [Azure DevOps 설정 — 네트워크 경로 선택](Azure-DevOps-설정.md#21-네트워크-경로-선택)을
참고하십시오.

## 8. 정책 검사의 의도적 한계

`SqlCmd.Common.psm1`은 GO 분리를 `Microsoft.SqlTools.ManagedBatchParser`에 전적으로
위임합니다. 저장소는 새 SQL lexer/tokenizer/state machine을 구현하지 않습니다.

`Test-DeploymentScript.ps1`과 인스턴스 스크립트 검사는 batch text 정규식 수준입니다.
주석·문자열·quoted identifier 안의 단어를 오탐하거나, 복잡한 동적 SQL과 비정형 표기를
놓칠 수 있습니다. **이를 코드 예외로 보완하지 않습니다.** 생성된 `deploy.sql`과
`database/instance`의 소수 스크립트는 DBA가 사람 review해야 합니다.

배포 스크립트 게이트의 규칙과 severity입니다.

| 규칙 | Severity | 대상 |
|---|---|---|
| DEPLOY001 / DEPLOY002 | error | `DROP TABLE`, `DROP COLUMN` |
| DEPLOY003 / DEPLOY004 | 조건부 | `DROP INDEX`, `DROP CONSTRAINT`. 같은 script에 동일 이름의 `CREATE`/`ADD`가 있으면 warning, 없으면 error |
| DEPLOY005 | error | `TRUNCATE TABLE` |
| DEPLOY006 | warning | 축소 가능 `ALTER COLUMN` |
| DEPLOY007 | warning | `sp_rename` |
| DEPLOY008 | error | 검토할 수 없는 동적 SQL |
| DEPLOY009 | warning | `SET NOEXEC` |
| DEPLOY010 | error | 분석 불가능한 `EXEC` 경로 |

`DROP INDEX`와 `DROP CONSTRAINT`를 조건부로 둔 이유는, DacFx가 인덱스에 included column을
추가하거나 제약을 변경할 때 일상적으로 DROP+CREATE를 생성하기 때문입니다. 이를 무조건
error로 두면 정상적인 인덱스 튜닝이 전부 차단되고 결국 allowlist를 남발하게 됩니다.

allowlist는 티켓과 만료일이 있는 한시적 예외만 허용합니다.
