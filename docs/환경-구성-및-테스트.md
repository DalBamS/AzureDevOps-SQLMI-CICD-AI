# 개발 환경 구성 및 테스트 가이드

이 문서는 저장소의 실행 가능한 skeleton을 로컬과 Azure DevOps에서 검증하는 절차를 설명합니다.

## 1. 저장소 구조

```text
.
├─ database/App.Database/          SDK-style SQL 프로젝트
│  ├─ Schemas/                     사용자 스키마
│  ├─ Tables/                      테이블 및 확장 속성 메타데이터
│  ├─ Views/                       뷰
│  ├─ StoredProcedures/            저장 프로시저
│  └─ Scripts/                     빌드 모델에서 제외되는 배포 후 스크립트
├─ tests/integration/              DACPAC 배포 후 실행하는 SQL 스모크 테스트
├─ eng/                            빌드, 정책, 컨테이너 테스트, BACPAC 도구
├─ pipelines/templates/            환경 배포 stage 템플릿
├─ ai/                             AI 데이터베이스 변경 리뷰 지침
├─ NuGet.config                    재현 가능한 Microsoft.Build.Sql 복원 소스
└─ azure-pipelines.yml             CI/CD 진입점
```

## 2. 필수 도구

| 도구 | 용도 | 최소 기준 |
|---|---|---|
| .NET SDK | Microsoft.Build.Sql 빌드와 SqlPackage 실행 | .NET 10 SDK |
| PowerShell 7 | `eng/*.ps1` 실행 | 7.4 이상 권장 |
| Azure CLI | SQL MI Entra 토큰 및 BACPAC 작업 | 최신 안정 버전 |
| VS Code SQL Database Projects 확장 | 선택적 GUI 개발 | 최신 안정 버전 |

`global.json`은 .NET 10 feature band 내 roll-forward를 허용합니다. `dotnet --info` 결과에 SDK가 없으면 runtime만 설치된 상태이므로 SDK를 별도로 설치해야 합니다.

## 3. Azure DevOps 중심 테스트

### 3.1 선택적 로컬 정적 빌드

```powershell
pwsh ./eng/Build.ps1
```

결과:

```text
artifacts/dacpac/App.Database.dacpac
```

빌드는 다음 항목을 검사합니다.

- SQL Server 2022/SQL MI 대상 플랫폼(`Sql160DatabaseSchemaProvider`) 모델 유효성
- SQL 참조 및 구문
- Microsoft.Build.Sql 코드 분석
- Release 구성의 T-SQL warning-as-error

현재 skeleton은 SQL Server 2022 호환성을 SQL MI 기준선으로 사용합니다. 대상 SQL MI가 다른 엔진 기준을 요구하면 `.sqlproj`의 `DSP`를 해당 SQL Server target platform으로 변경하고 Dev 환경에서 호환성을 확인합니다.

### 3.2 선택적 로컬 SQL 정책 검사

```powershell
pwsh ./eng/Test-SqlPolicy.ps1
```

`artifacts/sql-policy-report.md`를 생성합니다. 파괴적 `DROP`, `TRUNCATE`는 실패시키고 `SELECT *`, `NOLOCK`은 검토 경고로 기록합니다. 실제 운영 정책은 `eng/Test-SqlPolicy.ps1`의 규칙 목록을 조직 표준에 맞게 확장합니다.

### 3.3 PR 통합 테스트

SQL 변경 브랜치를 push하고 `main` 대상 PR을 생성합니다.

```powershell
git push --set-upstream origin <branch-name>
```

GitHub에서 `main` 대상 PR을 생성합니다. Azure DevOps의 `IntegrationTest` job은
Microsoft-hosted `ubuntu-latest` agent에서
`eng/Test-Database.ps1`을 실행합니다.

1. DACPAC 빌드
2. 고정 버전 SqlPackage 설치
3. 임시 SQL Server 2022 컨테이너 시작
4. `AppDb_Test` 데이터베이스에 DACPAC 게시
5. `tests/integration/*.sql`을 파일명 순서대로 실행
6. 임시 컨테이너와 암호 제거

컨테이너는 Azure DevOps agent 안에서만 사용하므로 개발 PC에 Docker Desktop을 설치할
필요가 없습니다. `Test-Database.ps1`은 파이프라인 재현과 agent 장애 조사용 내부
명령으로 유지합니다.

### 3.4 AI SQL 리뷰

AI 리뷰는 결정론적 정책 검사를 대체하지 않고 SQL 변경의 설계 및 배포 위험을 보강합니다.
PR에서는 SQL diff를 검토해 GitHub 코멘트와 pipeline artifact를 생성하고, 환경 배포
전에는 실제 `deploy.sql`을 다시 검토합니다. Azure Pipelines의 Workload Identity
Federation과 Entra ID 인증을 사용하므로 API key를 저장하지 않습니다.

### 3.5 실제 SQL MI 환경 배포

PR 검증과 병합이 끝나면 Azure DevOps에서 파이프라인을 수동 실행합니다.

| Parameter | 결과 |
|---|---|
| `deployDev=true` | `AppDb_CicdDemo_Dev` 배포 및 SQL MI 스모크 테스트 |
| `deployTest=true` | Test 승인 후 `AppDb_CicdDemo_Stg` 배포 및 테스트 |
| `deployProd=true` | Prod 승인 후 `AppDb_CicdDemo_Live` 배포 및 테스트 |

세 환경은 동일한 immutable DACPAC을 순서대로 사용합니다. 각 배포 직후
`eng/Test-DeployedDatabase.ps1`이 `tests/integration/*.sql`을 실제 SQL MI에서
실행합니다. 현재 Demo는 한 SQL MI 안에서 데이터베이스를 분리한 구성이며 실제 운영
환경에서는 Prod SQL MI를 별도 인스턴스로 분리합니다.

### 3.6 반복 테스트와 초기화

테스트 브랜치를 push해도 `main` 내용은 변경되지 않습니다. `main`은 PR을 merge했을 때만
변경됩니다. 반복 테스트는 매번 최신 `main`에서 새 브랜치를 만듭니다.

```powershell
$testBranch = 'demo/sql-change-01'

git switch main
git pull --ff-only origin main
git switch -c $testBranch

# database/App.Database 및 필요한 tests/integration 파일 수정
git add ./database/App.Database ./tests/integration
git commit -m "Test database change"
git push --set-upstream origin $testBranch
```

테스트만 수행하는 PR은 merge하지 않고 닫습니다. 테스트 종료 후 브랜치와 로컬 생성물을
다음 순서로 정리합니다.

```powershell
$testBranch = 'demo/sql-change-01'

git switch main
git pull --ff-only origin main

# 테스트 브랜치의 commit을 더 이상 보관하지 않을 때만 실행
git branch -D $testBranch
git push origin --delete $testBranch

pwsh ./eng/Clear-GeneratedArtifacts.ps1
git status
```

`Clear-GeneratedArtifacts.ps1`은 `artifacts`, `TestResults`, `bin`, `obj`만 삭제합니다.
`App.Database.sqlproj`와 SQL 소스는 삭제하지 않습니다. 테스트 브랜치에 commit하지 않은
변경이 남아 있으면 먼저 보관하거나 다음 명령으로 명시적으로 폐기한 후 `main`으로
전환합니다.

```powershell
# 아래 두 명령은 해당 경로의 미커밋 변경과 새 파일을 영구 삭제합니다.
git restore --staged --worktree -- ./database/App.Database ./tests/integration
git clean -nd -- ./database/App.Database ./tests/integration
git clean -fd -- ./database/App.Database ./tests/integration
```

테스트 PR을 이미 merge했다면 `main`을 강제로 이전 commit으로 reset하거나 force-push하지
않습니다. 별도 브랜치에서 merge commit을 되돌리는 PR을 만듭니다.

```powershell
git switch main
git pull --ff-only origin main
git switch -c revert/demo-sql-change
git revert <merge-commit-sha>
git push --set-upstream origin revert/demo-sql-change
```

Demo SQL MI도 배포 전의 빈 상태로 되돌리려면 먼저 대상 확인만 수행합니다.

```powershell
$resourceGroup = '<sql-mi-resource-group>'
$managedInstance = '<sql-mi-name>'
$sqlServer = '<sql-mi-public-fqdn>'
$deployerPrincipal = '<deployer-principal-name>'

az sql mi start -g $resourceGroup --mi $managedInstance
$token = az account get-access-token `
  --resource 'https://database.windows.net/' `
  --query accessToken `
  --output tsv

& ./eng/Reset-DemoDatabases.ps1 `
  -ServerName $sqlServer `
  -Port 3342 `
  -DatabaseName @('AppDb_CicdDemo_Dev', 'AppDb_CicdDemo_Stg', 'AppDb_CicdDemo_Live') `
  -DeployerPrincipalName $deployerPrincipal `
  -AccessToken $token `
  -ConfirmReset `
  -WhatIf
```

출력된 세 데이터베이스가 정확한 경우 `-WhatIf`만 제거해 실행합니다. 이 작업은
`AppDb_CicdDemo_*` 데이터와 스키마를 영구 삭제하고 빈 DB와 배포 계정 권한만
재생성합니다. 이후 `main` 기준 Azure DevOps 배포를 실행하면 최초 Demo 상태가 다시
구성됩니다. 실제 운영 DB에는 이 스크립트를 사용하지 않습니다.

Azure DevOps 실행 기록과 artifact는 감사 이력이므로 다음 테스트에 영향을 주지 않으며
초기화 과정에서 삭제하지 않습니다.

## 4. 데이터베이스 프로젝트 확장 규칙

### 스키마 오브젝트

- 선언적 최종 상태는 `database/App.Database` 아래 오브젝트 종류별 폴더에 저장합니다.
- 한 파일에 주 데이터베이스 오브젝트 하나를 둡니다.
- 테이블/컬럼 설명은 `MS_Description` 확장 속성으로 함께 버전 관리합니다.
- 환경별 서버명, 사용자명, 암호를 SQL 프로젝트에 넣지 않습니다.

### 정적 데이터

- 작은 참조 데이터만 `Scripts/Seed`에 둡니다.
- 모든 스크립트는 재실행 가능한 idempotent 형태여야 합니다.
- 대량 데이터 이동은 BACPAC 또는 별도 ETL/마이그레이션 작업으로 분리합니다.

### 위험한 변경

컬럼 제거, 타입 축소, 대형 테이블의 NOT NULL 변경은 한 번에 수행하지 않습니다.

1. Expand: 신규 컬럼/오브젝트 추가
2. Migrate: 데이터 백필 및 이중 쓰기
3. Contract: 소비 코드 전환 확인 후 구 오브젝트 제거

`BlockOnPossibleDataLoss=True`는 최후 방어선이지 마이그레이션 설계를 대신하지 않습니다.

## 5. BACPAC 사용

SqlPackage를 설치하고 Azure CLI로 로그인한 뒤 실행합니다.

```powershell
dotnet tool install --global Microsoft.SqlPackage --version 170.4.83 --allow-roll-forward
az login

pwsh ./eng/Export-Bacpac.ps1 `
  -ServerName 'my-mi.public.xxxxx.database.windows.net' `
  -Port 3342 `
  -DatabaseName 'AppDb' `
  -OutputPath './artifacts/backup/AppDb.bacpac'

pwsh ./eng/Import-Bacpac.ps1 `
  -ServerName 'my-test-mi.public.xxxxx.database.windows.net' `
  -Port 3342 `
  -DatabaseName 'AppDb_Seeded' `
  -BacpacPath './artifacts/backup/AppDb.bacpac'
```

BACPAC에는 데이터가 포함될 수 있으므로 Git에 커밋하지 않습니다. 민감 데이터는 Test 환경 반입 전에 마스킹하고, 운영 export는 일관된 복사본이나 업무 정지 구간에서 수행합니다.

SQL MI private endpoint는 일반적으로 1433을 사용하므로 `-Port`를 생략할 수 있습니다. Public endpoint는 3342를 지정합니다.

## 6. 완료 기준

- `Build.ps1`이 DACPAC을 생성한다.
- `Test-SqlPolicy.ps1`이 오류 없이 보고서를 생성한다.
- Azure DevOps hosted container에서 두 integration test가 통과한다.
- Azure DevOps CI가 동일 DACPAC을 immutable artifact로 게시한다.
- Dev/Stg/Live SQL MI 데이터베이스에서 배포 후 integration test가 통과한다.
- Test와 Prod 배포가 Environment 승인 없이 진행되지 않는다.
- 각 환경의 `deploy.sql`, `deploy-report.xml`, `ai-review.json`을 검토할 수 있다.
