# 개발 환경 구성 및 테스트 가이드

이 문서는 저장소의 실행 가능한 skeleton을 로컬과 Azure DevOps에서 검증하는 절차를 설명합니다.

## 1. 저장소 구조

```text
.
├─ database/App.Database/          SDK-style SQL 프로젝트
│  ├─ Schemas/                     사용자 스키마
│  ├─ Tables/                      테이블 및 확장 속성 메타데이터
│  ├─ Views/                       뷰
│  ├─ StoredProcedures/            저장 프로시저
│  └─ Scripts/                     빌드 모델에서 제외되는 배포 후 스크립트
├─ database/instance/              멱등 SQL MI 로그인·SQL Agent job 스크립트
├─ tests/integration/              DACPAC 배포 후 실행하는 SQL 스모크 테스트
├─ eng/                            빌드, 정책, 컨테이너 테스트, BACPAC 도구
│  └─ policy/                      배포 스크립트 게이트 allowlist
├─ pipelines/profiles/             연결 정보 없는 환경별 DAC publish profile
├─ pipelines/templates/            환경 배포 stage 템플릿
├─ ai/                             AI 데이터베이스 변경 리뷰 지침
├─ NuGet.config                    재현 가능한 Microsoft.Build.Sql 복원 소스
└─ azure-pipelines.yml             CI/CD 진입점
```

## 2. 필수 도구

| 도구 | 용도 | 최소 기준 |
|---|---|---|
| .NET SDK | Microsoft.Build.Sql 빌드와 SqlPackage 실행 | .NET 10 SDK |
| PowerShell 7 | `eng/*.ps1` 실행 | 7.4 이상 권장 |
| Azure CLI | SQL MI Entra 토큰 및 BACPAC 작업 | 최신 안정 버전 |
| VS Code SQL Database Projects 확장 | 선택적 GUI 개발 | 최신 안정 버전 |

`global.json`은 .NET 10 feature band 내 roll-forward를 허용합니다. `dotnet --info` 결과에 SDK가 없으면 runtime만 설치된 상태이므로 SDK를 별도로 설치해야 합니다.
`App.Database.sqlproj`는 `Microsoft.Build.Sql` 2.2.0을 고정하며, 해당 공식 package는
.NET 8 이상을 요구합니다.

- [Microsoft.Build.Sql 2.2.0](https://www.nuget.org/packages/Microsoft.Build.Sql/2.2.0)

## 3. Azure DevOps 중심 테스트

### 3.1 선택적 로컬 정적 빌드

```powershell
pwsh ./eng/Build.ps1
pwsh ./eng/Build.ps1 -Strictness Lenient
pwsh ./eng/Build.ps1 -Strictness Balanced
pwsh ./eng/Build.ps1 -Strictness Strict
```

결과:

```text
artifacts/dacpac/App.Database.dacpac
```

빌드는 다음 항목을 검사합니다.

- SQL Server 2025/SQL MI 대상 플랫폼(`Sql170DatabaseSchemaProvider`) 모델 유효성
- SQL 참조 및 구문
- Microsoft.Build.Sql 코드 분석
- 선택한 `BuildStrictness`의 T-SQL warning 정책(기본 `Strict`)

엄격도는 다음 세 단계로 운영합니다.

| 모드 | 코드 분석 | warning-as-error | 억제 |
|---|---|---|---|
| `Lenient` | 실행 | 아니요(경고 수집) | 없음 |
| `Balanced` | 실행 | 예 | 호출자가 검증해 전달한 `ValidatedSuppressTSqlWarnings`만 |
| `Strict` | 실행 | 예 | 없음 |

도입 기준은 숫자로 관리합니다. 먼저 Lenient를 **연속 10회 CI** 실행해 모든 warning을
소유자/티켓과 함께 분류합니다. 미분류 warning이 **0개**이고 baseline 변동이 **3회 연속
0개**이면 Balanced로 전환해 검증된 번호만 쉼표 목록으로 전달합니다. suppress 목록이
**0개**가 되고 **20회 연속 CI에서 신규 warning 0개**를 달성하면 Strict를 기본/필수로
전환합니다. 실제 warning 번호를 확인하기 전에는 임의 번호를 baseline에 넣지 않습니다.

현재 저장소 기준선은 SQL Server 2025입니다. SQL MI update policy, SQL 프로젝트 DSP,
로컬 컨테이너 이미지는 다음처럼 함께 변경해야 합니다. Microsoft 문서상 기존 인스턴스와
신규 인스턴스의 기본 update policy는 SQL Server 2022이므로 이 저장소를 실제 SQL MI에
배포하기 전에 SQL Server 2025 policy를 명시적으로 선택하고 적용 상태를 확인해야 합니다.

| SQL MI update policy | SQL 프로젝트 DSP | 검증 컨테이너 | 운영 규칙 |
|---|---|---|---|
| SQL Server 2022 | `Sql160DatabaseSchemaProvider` | `2022-latest` | 레거시 브랜치에서만 사용 |
| SQL Server 2025 | `Sql170DatabaseSchemaProvider` | `2025-latest` | 현재 저장소 기준선 |
| Always-up-to-date | `Sql170DatabaseSchemaProvider` 이상 | `2025-latest`를 최소 기준으로 사용 | Azure 전용 최신 기능은 Dev SQL MI에서 추가 검증 |

SQL Server 2022 mainstream support는 **2028-01-11**에 종료됩니다. Microsoft 안내에
따르면 SQL MI의 SQL Server 2022 update policy도 그 시점까지만 제공되고 이후 당시
최신 주요 버전에 해당하는 정책으로 자동 전환됩니다. 전환 전에 DSP, 컨테이너, 복원 및
MI Link 요구사항을 함께 재검증합니다.

- [SQL MI update policy](https://learn.microsoft.com/azure/azure-sql/managed-instance/update-policy)
- [SQL Server 2022 lifecycle](https://learn.microsoft.com/lifecycle/products/sql-server-2022)
- [SQL 프로젝트 target platform과 DSP](https://learn.microsoft.com/sql/tools/sql-database-projects/concepts/target-platform)

`ModelCollation`은 빌드 모델 비교 동작이며 실제 대상 데이터베이스 collation을 보장하지
않습니다. `ScriptDatabaseOptions=False`이므로 배포가 collation 변경을 시도하지 않으며,
대상 생성 시점과 배포 전 점검에서 collation을 별도로 확인해야 합니다.

### 3.2 선택적 로컬 SQL 정책 검사

```powershell
pwsh ./eng/Test-SqlPolicy.ps1
```

`artifacts/sql-policy-report.md`를 생성합니다. Seed를 포함한 모든 SQL 소스에서
`DELETE`, `TRUNCATE`, 비멱등 배포 스크립트를 오류로 검사하고 `SELECT *`, `NOLOCK`은
경고로 기록합니다. 실제 배포 계획의 파괴 DDL은 소스 텍스트가 아니라
`eng/Test-DeploymentScript.ps1`이 생성된 `deploy.sql`에서 담당합니다.

### 3.3 PR 통합 테스트

SQL 변경 브랜치를 push합니다.

```powershell
git push --set-upstream origin <branch-name>
```

GitHub에서 `main` 대상 PR을 생성하면 Azure DevOps의 `IntegrationTest` job이
Microsoft-hosted `ubuntu-latest` agent에서 `eng/Test-Database.ps1`을 실행합니다.

1. DACPAC 빌드
2. NuGet tool package `Microsoft.SqlPackage` 170.4.83 설치
3. 임시 SQL Server 2025 컨테이너 시작 후 컨테이너 내부의 실제 `sqlcmd` 경로 탐색
4. `AppDb_Test` 데이터베이스에 DACPAC 게시
5. `tests/integration/*.sql`을 파일명 순서대로 실행
6. 임시 컨테이너와 암호 제거

컨테이너는 Azure DevOps agent 안에서만 사용하므로 개발 PC에 Docker Desktop을 설치할
필요가 없습니다. `Test-Database.ps1`은 파이프라인 재현과 agent 장애 조사용 내부
명령으로 유지합니다.

### 3.4 AI SQL 리뷰

AI 리뷰는 결정론적 정책 검사를 대체하지 않고 SQL 변경의 설계 및 배포 위험을 보강합니다.
PR에서는 SQL diff를 검토해 GitHub 코멘트와 pipeline artifact를 생성하고, 환경 배포
전에는 실제 `deploy.sql`을 다시 검토합니다. Azure Pipelines의 Workload Identity
Federation과 Entra ID 인증을 사용하므로 API key를 저장하지 않습니다.

입력이 `MaxInputCharacters`(기본 120000)를 넘으면 독립 줄 `GO`를 우선 경계로
순차 검토합니다. 하나의 배치가 제한보다 크면 줄 경계를 사용하고, 물리적 한 줄 자체가
제한보다 클 때만 고정 문자 창으로 나눕니다. fallback은 문자를 삭제하거나 바꾸지 않는
무손실 방식이며 결과는 `low < medium < high` 최댓값과 최초 등장 순서의 중복 제거로
병합됩니다. 각 요청에는 원본 경로와 시작 줄이 포함되며 응답의 청크 상대 줄은 원본 전역
줄로 변환됩니다. Git diff는 `core.quotePath=false`로 생성하고 외부 diff의 C-style quoted
UTF-8 경로도 복원해 파일과 hunk별 새 파일 줄 매핑을 사용합니다. 네트워크 없는 회귀는
다음 명령으로 실행합니다.

```powershell
pwsh ./eng/Test-AiDatabaseReview.ps1
```

### 3.5 실제 SQL MI 환경 배포

PR 검증과 병합이 끝나면 Azure DevOps에서 파이프라인을 수동 실행합니다.

| Parameter | 결과 |
|---|---|
| `deployDev=true` | `AppDb_CicdDemo_Dev` 배포 및 SQL MI 스모크 테스트 |
| `deployTest=true` | Test 승인 후 `AppDb_CicdDemo_Stg` 배포 및 테스트 |
| `deployProd=true` | Prod 승인 후 `AppDb_CicdDemo_Live` 배포 및 테스트 |
| `maxParallel=4` | 카나리 통과 뒤 나머지 DB의 최대 동시 배포 수 |
| `validateAllDatabasePlans=false` | 대표 DB만 계획; `true`이면 모든 DB DeployReport 생성 |
| `databasePlanDriftPolicy=Warn` | 전수 계획 차이를 경고 또는 `Fail`로 차단 |
| `deployInstanceObjects=false` | DB fan-out 성공 후 인스턴스 오브젝트 job 실행 |

Variable group의 `databaseNames`에 쉼표 구분 목록을 지정합니다. 값이 없거나 변수가
정의되지 않았으면 기존 `databaseName` 단일 값을 사용합니다. 목록 첫 항목만 Plan의 대표
DB이자 카나리이며, 카나리 publish와 `Test-DeployedDatabase.ps1`이 성공해야
`Start-ThreadJob` throttle 기반 나머지 fan-out이 시작됩니다. 모든 DB의 결과를 수집한 후
하나라도 실패하면 stage가 실패하고 실패 목록과 성공/실패 수가 Azure DevOps summary에
게시됩니다. 런타임 문자열을 compile-time `each`로 확장하지 않습니다.

기본 계획은 대표 DB 하나만 조회하므로 비용이 낮습니다. `validateAllDatabasePlans=true`는
각 DB의 DeployReport를 artifact에 추가하고 대표 계획과 비교합니다. 차이는 `Warn`이면
승인자에게 경고하고 DB별 보고서를 승인 기준으로 보존하며, `Fail`이면 Plan을 중단합니다.
기본 대표 전용 모드는 실제 배포 직전에 각 DB의 작업 집합을 승인된 대표 보고서와 비교하고,
전수 모드는 각 DB의 현재 보고서를 해당 DB의 승인 보고서와 비교합니다.

별도 `pipelines/drift-report.yml`은 매일 02:00 UTC에 Dev/Test/Prod를 점검합니다.
각 환경의 `databaseNames` 첫 항목만 대표 DB로 선택해 비용을 환경당 DeployReport 1회로
제한합니다. 변경이 없으면 성공하고, 변경이 있으면 DB별 환경 artifact를 게시하며
`SucceededWithIssues`로 표시합니다. 인증, 네트워크, SqlPackage 또는 XML 오류는 경고로
바꾸지 않고 실패합니다. 이 파이프라인은 `/Action:DeployReport`만 허용하며 배포 액션을
호출하지 않습니다.

Dev/Test/Prod는 각각 이름만 다른 publish profile을 사용하지만 세 XML의 속성은 완전히
동일합니다. 각 환경에서 `Script`, `DeployReport`, `Publish`가 반드시 해당 환경의 같은
profile을 사용합니다. profile에는 서버, 데이터베이스, 사용자, 암호를 넣지 않습니다.

SqlPackage의 `CommandTimeout` 속성 기본값은 60초입니다. 장기 MI DDL에는 부족할 수
있으므로 profile은 3600초를 명시하며 파이프라인 `sqlCommandTimeout` parameter 또는
로컬의 같은 이름 환경 변수로만 재정의합니다. 연결 수립 제한인 connection string의
`Connection Timeout=30`과 실행 명령 제한인 `CommandTimeout`을 혼동하지 않습니다.
`Microsoft.SqlPackage` tool package 170.4.83을 설치하면 현재 검증된 CLI
`/Version` 출력은 `170.4.83.3`입니다.

- [SqlPackage 170.4.83.3 release notes](https://learn.microsoft.com/sql/tools/sqlpackage/release-notes-sqlpackage#1704833-sqlpackage)

`Plan*` stage는 `deploy.sql` 생성 직후 결정론적 게이트를 실행합니다. 오류가 하나라도
있으면 stage를 실패시키고, 경고·오류·allowlist 적용 결과는
`deployment-script-policy.md`로 게시합니다. 탐지 범위는 `DROP TABLE/COLUMN/INDEX/
CONSTRAINT`, `TRUNCATE TABLE`, 축소 가능 `ALTER COLUMN`, `sp_rename`,
`sp_executesql` 동적 DDL, `SET NOEXEC`입니다. AI 검토와 사람 승인은 이 게이트를
대체하거나 우회하지 않습니다.

예외가 필요한 경우 `eng/policy/deploy-allowlist.json`에 다음 필드를 추가합니다.

```json
[
  {
    "rule": "DEPLOY001",
    "pattern": "\\[dbo\\]\\.\\[ApprovedLegacyTable\\]",
    "ticket": "CHG-1234",
    "expiresOn": "2026-08-31"
  }
]
```

`pattern`은 탐지된 statement에 적용되는 정규식입니다. 만료일이 지난 항목은 자동으로
무효가 되며 보고서의 expired 항목에 남습니다.

### 3.6 인스턴스 오브젝트와 재시도

`database/instance`의 `001-entra-login.sql`, `010-agent-job.sql`은 SQLCMD 변수로 실제
이름을 주입하며 존재 여부에 따라 생성/갱신합니다. `deployInstanceObjects=true`일 때만
database fan-out 성공 후 별도 job에서 실행됩니다. Variable group에는
`instanceEntraLoginName`, `instanceAgentJobName`, `instanceAgentJobOwner`를 설정합니다.
파일은 `NNN-description.sql` 순서, `-- Idempotency:` 선언, 존재 검사와 비파괴 정책을
통과해야 합니다. 로컬 사전 확인:

```powershell
pwsh ./eng/Deploy-InstanceObjects.ps1 `
  -ServerName '<sql-mi-fqdn>' `
  -AccessToken '<access-token>' `
  -SqlcmdVariables @{
    EntraLoginName = '<entra-login-name>'
    AgentJobName = '<agent-job-name>'
    AgentJobOwner = '<job-owner-login>'
  } `
  -WhatIf
```

스크립트는 Azure CLI가 반환한 문자열 access token을 `Invoke-Sqlcmd -AccessToken`에
직접 전달합니다. 현재 SqlServer module 문서는 이 parameter에 문자열과 `SecureString`을
모두 허용합니다.

- [`Invoke-Sqlcmd -AccessToken`](https://learn.microsoft.com/powershell/module/sqlserver/invoke-sqlcmd#-accesstoken)

같은 immutable DACPAC 재시도는 안전합니다. 이미 목표 상태인 DB는 publish를 생략하고
스모크만 다시 실행하며, 변경이 남은 DB는 승인된 DeployReport 비교를 다시 통과해야 합니다.
Azure DevOps Plan은 각 DeployReport와 Script마다, rollout은 DeployReport, Publish,
smoke test마다
`eng/Get-AzureSqlAccessToken.ps1`을 호출해 만료되지 않은 토큰을 사용합니다.
실패 유형별 복구는 [롤백 런북](롤백-런북.md)을 따릅니다.

### 3.7 반복 테스트와 초기화

테스트 브랜치를 push해도 `main` 내용은 변경되지 않습니다. `main`은 PR을 merge했을 때만
변경됩니다. 반복 테스트는 매번 최신 `main`에서 새 브랜치를 만듭니다.

```powershell
$testBranch = 'demo/sql-change-01'

git switch main
git pull --ff-only origin main
git switch -c $testBranch

# database/App.Database 및 필요한 tests/integration 파일 수정
git add ./database/App.Database ./tests/integration
git commit -m "Test database change"
git push --set-upstream origin $testBranch
```

테스트만 수행하는 PR은 merge하지 않고 닫습니다. 테스트 종료 후 브랜치와 로컬 생성물을
다음 순서로 정리합니다.

```powershell
$testBranch = 'demo/sql-change-01'

git switch main
git pull --ff-only origin main

# 테스트 브랜치의 commit을 더 이상 보관하지 않을 때만 실행
git branch -D $testBranch
git push origin --delete $testBranch

pwsh ./eng/Clear-GeneratedArtifacts.ps1
git status
```

`Clear-GeneratedArtifacts.ps1`은 `artifacts`, `TestResults`, `bin`, `obj`만 삭제합니다.
`App.Database.sqlproj`와 SQL 소스는 삭제하지 않습니다. 테스트 브랜치에 commit하지 않은
변경이 남아 있으면 먼저 보관하거나 다음 명령으로 명시적으로 폐기한 후 `main`으로
전환합니다.

```powershell
# 아래 두 명령은 해당 경로의 미커밋 변경과 새 파일을 영구 삭제합니다.
git restore --staged --worktree -- ./database/App.Database ./tests/integration
git clean -nd -- ./database/App.Database ./tests/integration
git clean -fd -- ./database/App.Database ./tests/integration
```

테스트 PR을 이미 merge했다면 `main`을 강제로 이전 commit으로 reset하거나 force-push하지
않습니다. 별도 브랜치에서 merge commit을 되돌리는 PR을 만듭니다.

```powershell
git switch main
git pull --ff-only origin main
git switch -c revert/demo-sql-change
git revert <merge-commit-sha>
git push --set-upstream origin revert/demo-sql-change
```

Demo SQL MI도 배포 전의 빈 상태로 되돌리려면 먼저 대상 확인만 수행합니다.

```powershell
$resourceGroup = '<sql-mi-resource-group>'
$managedInstance = '<sql-mi-name>'
$sqlServer = '<sql-mi-public-fqdn>'
$deployerPrincipal = '<deployer-principal-name>'

az sql mi start -g $resourceGroup --mi $managedInstance
$token = az account get-access-token `
  --resource 'https://database.windows.net/' `
  --query accessToken `
  --output tsv

& ./eng/Reset-DemoDatabases.ps1 `
  -ServerName $sqlServer `
  -Port 3342 `
  -DatabaseName @('AppDb_CicdDemo_Dev', 'AppDb_CicdDemo_Stg', 'AppDb_CicdDemo_Live') `
  -DeployerPrincipalName $deployerPrincipal `
  -AccessToken $token `
  -ConfirmReset `
  -WhatIf
```

출력된 세 데이터베이스가 정확한 경우 `-WhatIf`만 제거해 실행합니다. 이 작업은
`AppDb_CicdDemo_*` 데이터와 스키마를 영구 삭제하고 빈 DB와 배포 계정 권한만
재생성합니다. 이후 `main` 기준 Azure DevOps 배포를 실행하면 최초 Demo 상태가 다시
구성됩니다. 실제 운영 DB에는 이 스크립트를 사용하지 않습니다.

Azure DevOps 실행 기록과 artifact는 감사 이력이므로 다음 테스트에 영향을 주지 않으며
초기화 과정에서 삭제하지 않습니다.

## 4. 데이터베이스 프로젝트 확장 규칙

### 스키마 오브젝트

- 선언적 최종 상태는 `database/App.Database` 아래 오브젝트 종류별 폴더에 저장합니다.
- 한 파일에 주 데이터베이스 오브젝트 하나를 둡니다.
- 테이블/컬럼 설명은 `MS_Description` 확장 속성으로 함께 버전 관리합니다.
- 환경별 서버명, 사용자명, 암호를 SQL 프로젝트에 넣지 않습니다.
- 사용자, 로그인, 권한, database/server role membership은 publish profile에서 제외합니다.
  DACPAC 밖의 승인된 보안 IaC 또는 DBA 절차로 관리하고 별도 감사 이력을 남깁니다.

### 정적 데이터

- 작은 참조 데이터만 `Scripts/Seed`에 둡니다.
- 모든 스크립트는 재실행 가능한 idempotent 형태여야 합니다.
- `usp_SeedFeatureFlags`처럼 seed 실행 진입점을 하나로 두고 통합 테스트에서 두 번 호출해
  행 수가 변하지 않는지 검증합니다.
- 대량 데이터 이동은 BACPAC 또는 별도 ETL/마이그레이션 작업으로 분리합니다.

### 위험한 변경

컬럼 제거, 타입 축소, 대형 테이블의 NOT NULL 변경은 한 번에 수행하지 않습니다.

1. Expand: 신규 컬럼/오브젝트 추가
2. Migrate: 데이터 백필 및 이중 쓰기
3. Contract: 소비 코드 전환 확인 후 구 오브젝트 제거

`BlockOnPossibleDataLoss=True`와 배포 스크립트 게이트는 최후 방어선이지 마이그레이션
설계를 대신하지 않습니다. `AllowIncompatiblePlatform`은 사용하지 않으므로 DSP와 SQL MI
update policy가 맞지 않으면 배포를 중단합니다.

## 5. BACPAC 사용

SqlPackage를 설치하고 Azure CLI로 로그인한 뒤 실행합니다.

```powershell
dotnet tool install --global Microsoft.SqlPackage --version 170.4.83 --allow-roll-forward
az login

pwsh ./eng/Export-Bacpac.ps1 `
  -ServerName 'my-mi.public.xxxxx.database.windows.net' `
  -Port 3342 `
  -DatabaseName 'AppDb' `
  -OutputPath './artifacts/backup/AppDb.bacpac'

pwsh ./eng/Import-Bacpac.ps1 `
  -ServerName 'my-test-mi.public.xxxxx.database.windows.net' `
  -Port 3342 `
  -DatabaseName 'AppDb_Seeded' `
  -BacpacPath './artifacts/backup/AppDb.bacpac'
```

BACPAC에는 데이터가 포함될 수 있으므로 Git에 커밋하지 않습니다. 민감 데이터는 Test 환경 반입 전에 마스킹하고, 운영 export는 일관된 복사본이나 업무 정지 구간에서 수행합니다.

같은 VNet 또는 peering/VPN/ExpressRoute에서 SQL MI의 **VNet-local endpoint**에
연결할 때는 일반적으로 1433을 사용하므로 `-Port`를 생략할 수 있습니다. **Private
endpoint**는 다른 VNet에 SQL MI를 선택적으로 노출하는 별도 기능입니다. Public
endpoint는 3342를 지정합니다.

  `-IncludeDockerLabA`로 Lab A를 검증한다.
