# Phase 4 의도적 실패 실습 랩

이 문서는 배포 안전장치가 실제로 실패하는 경로를 의도적으로 재현하고, 실패를 우회하지
않고 안전하게 복구하는 교육용 절차입니다.

> [!CAUTION]
> **운영 DB, 공유 개발 DB, 실제 Azure SQL MI에서 이 랩을 실행하지 마십시오.**
> 전용 로컬 SQL Server 2025 컨테이너 또는 폐기 가능한 교육 환경만 사용하십시오.
> `labs/`의 SQL에는 파괴 DDL과 대량 작업이 포함되어 있습니다.

기본 오프라인 회귀는 다음 명령으로 실행합니다. Lab B~D에서 기대한 내부 명령의
non-zero를 검증한 뒤 전체 테스트가 성공했으므로 최종 exit code는 `0`입니다. 생성한
임시 JSON, Markdown, DB, 컨테이너는 `finally`에서 정리합니다.

```powershell
pwsh ./eng/Test-FailureLabs.ps1
# 예상 exit code: 0
```

## Lab A — BlockOnPossibleDataLoss

### 목적

데이터가 있는 `[app].[FeatureFlag].[LegacyDescription]` 컬럼을 DACPAC 원본에 없는
오브젝트로 만든 뒤, `DropObjectsNotInSource=True`와
`BlockOnPossibleDataLoss=True`로 publish하여 SqlPackage가 컬럼 제거를 차단하는지
확인합니다. 이어서 expand → migrate → contract를 한 단계씩 실행합니다.

### 사전 조건

- Docker Desktop 또는 Docker Engine, .NET 10 SDK, PowerShell 7이 필요합니다.
- `14334` 포트를 사용할 수 있어야 합니다. 충돌하면 `-HostPort`에 다른 포트를
  지정합니다.
- 스크립트는 `mcr.microsoft.com/mssql/server:2025-latest` 이미지를 사용하고
  SqlPackage `170.4.83`을 임시 디렉터리에 설치합니다.
- 시작 전 현재 대상이 운영/공유 DB가 아닌 전용 로컬 환경인지 다시 확인합니다.

### 재현 절차(명령 포함)

```powershell
New-Item -ItemType Directory -Force ./artifacts/labs | Out-Null
pwsh ./eng/Build.ps1
# 2026-08-02 실측 exit code: 0
# artifact: artifacts/dacpac/App.Database.dacpac

pwsh ./eng/Test-FailureLabs.ps1 -IncludeDockerLabA 2>&1 |
  Tee-Object ./artifacts/labs/lab-a.log
# 2026-08-02 실측 최종 exit code: 0
# 내부의 두 번째 SqlPackage publish 실측 exit code: 1
# artifact: artifacts/labs/lab-a.log
```

자동 검증은 기준 DACPAC을 `Phase4LabA`에 배포하고
[`setup-data-loss.sql`](../labs/lab-a-data-loss/setup-data-loss.sql)로 데이터가 든
컬럼을 추가한 다음, 같은 DACPAC을 `DropObjectsNotInSource=True`로 다시 publish합니다.
그 후 아래 실행 가능한 SQL을 순서대로 적용합니다.

1. Expand:
   [`01-expand.sql`](../labs/lab-a-data-loss/recovery/01-expand.sql) — nullable
   `DescriptionV2` 추가, 실측 exit code `0`
2. Migrate:
   [`02-migrate.sql`](../labs/lab-a-data-loss/recovery/02-migrate.sql) — 백필·검증 후
   NOT NULL 전환, 실측 exit code `0`
3. Contract:
   [`03-contract.sql`](../labs/lab-a-data-loss/recovery/03-contract.sql) — 새 컬럼 일치
   검증 후 구 컬럼 제거, 실측 exit code `0`

### 기대 결과(실제 오류 메시지 또는 artifact 발췌)

Windows Docker Desktop, SQL Server 2025 image, SqlPackage 170.4.83에서 2026-08-02
실측한 핵심 오류는 다음과 같습니다.

```text
Error SQL72014: Core Microsoft SqlClient Data Provider: 메시지 50000, 수준 16,
상태 127, 줄 6 행이 발견되었습니다. 데이터가 손실될 수 있으므로 스키마 업데이트가 종료됩니다.
```

`artifacts/labs/lab-a.log`의 마지막에는 다음 성공 문구가 남습니다.

```text
Lab A Docker data-loss block and expand-migrate-contract recovery passed.
```

### 복구 절차

실패한 publish의 `BlockOnPossibleDataLoss`를 즉시 끄지 않습니다. 애플리케이션이 구
컬럼을 읽는 동안 `01-expand.sql`로 신규 컬럼을 추가하고, `02-migrate.sql`로 작은
배치 단위의 실제 운영용 백필 절차를 설계합니다. 읽기·쓰기가 신규 컬럼으로 전환되고
관찰 기간이 끝난 뒤에만 `03-contract.sql`과 같은 검증 포함 contract를 별도 승인
변경으로 실행합니다. 자동 랩은 이 순서를 검증한 뒤 컨테이너를 삭제합니다.

### 강사 노트(수강생이 흔히 하는 오해)

- `BlockOnPossibleDataLoss=False`는 복구가 아니라 방어선 제거입니다.
- 컬럼 값이 현재 보존 가능해 보여도 DacFx는 상태 차이를 기준으로 위험을 판단합니다.
- 예제는 교육 시간을 위해 한 번에 백필합니다. 운영 대형 테이블에서는 배치 크기,
  로그 사용량, 잠금, 재시작 지점을 별도로 설계해야 합니다.
- contract는 expand와 같은 배포에 넣지 않습니다.

## Lab B — 승인 후 드리프트

> 이 랩은 실제 SQL MI 환경에서 미검증입니다. 강의 전 리허설이 필요합니다.

### 목적

Plan이 끝나 승인 대기 중일 때 대상 DB에 수동 DDL이 들어오면, Deploy 직전 새로 만든
report가 승인 report와 달라져
[`Confirm-DeploymentPlan.ps1`](../eng/Confirm-DeploymentPlan.ps1)이 배포를
차단하는지 확인합니다. 다중 샤드에서는 대상별 메타데이터가 달라도
`Operations`만 비교하는 Phase 2 계약을 사용합니다.

### 사전 조건

- 오프라인 재현에는 PowerShell 7만 필요합니다.
- 실제 흐름을 교육 DB에서 재현할 때는 Plan 단계의
  `artifacts/deployment-review-<environment>/deploy-report.xml`, 같은 DACPAC,
  같은 publish profile, 대상 DB 접속 권한이 필요합니다.
- [`manual-drift.sql`](../labs/lab-b-approved-drift/manual-drift.sql)은 전용 교육
  DB에서만 실행합니다.

### 재현 절차(명령 포함)

완전 오프라인 fixture 비교:

```powershell
New-Item -ItemType Directory -Force ./artifacts/labs | Out-Null
pwsh ./eng/Confirm-DeploymentPlan.ps1 `
  -ApprovedReportPath ./labs/lab-b-approved-drift/approved-report.xml `
  -CurrentReportPath ./labs/lab-b-approved-drift/current-after-drift-report.xml `
  -CompareOperationsOnly 2>&1 |
  Tee-Object ./artifacts/labs/lab-b-confirm.log
# 예상 exit code: non-zero
# artifact: artifacts/labs/lab-b-confirm.log
```

Plan → 승인 대기 → 수동 DDL → Deploy 차단 흐름은 폐기 가능한 교육 DB에서 다음 순서로
재현합니다.

```powershell
# 1. New-DatabaseDeploymentPlan.ps1이 만든 승인 대상
$approved = './artifacts/deployment-review-lab/deploy-report.xml'

# 2. 승인 대기 중 수동 변경
sqlcmd -S $server -d $database -G `
  -i ./labs/lab-b-approved-drift/manual-drift.sql -b
# 예상 exit code: 0

# 3. 같은 DACPAC/profile로 현재 report 재생성
SqlPackage /Action:DeployReport `
  /SourceFile:./artifacts/dacpac/App.Database.dacpac `
  "/TargetConnectionString:$connectionString" `
  /AccessToken:$accessToken `
  /Profile:./pipelines/profiles/sqlmi-dev.publish.xml `
  /OutputPath:./artifacts/labs/lab-b-current.xml
# 예상 exit code: 0
# artifact: artifacts/labs/lab-b-current.xml

# 4. Deploy-Databases.ps1과 동일한 shard-aware 비교
pwsh ./eng/Confirm-DeploymentPlan.ps1 `
  -ApprovedReportPath $approved `
  -CurrentReportPath ./artifacts/labs/lab-b-current.xml `
  -CompareOperationsOnly
# 예상 exit code: non-zero
```

### 기대 결과(실제 오류 메시지 또는 artifact 발췌)

오프라인 fixture는 서로 다른 `TargetDatabase` 메타데이터를 가지며, 차단 원인은
메타데이터가 아니라 `Operations`의 추가 `Drop` 항목입니다.

```text
The target database changed after approval. Generate and approve a new deployment plan.
```

`artifacts/labs/lab-b-confirm.log`에 위 문구가 기록되고 프로세스는 non-zero로
종료합니다. `eng/Test-FailureLabs.ps1`은 이 non-zero와 핵심 문구를 모두 확인합니다.

### 복구 절차

수동 변경을 숨기거나 approved report를 복사해 덮어쓰지 않습니다. 변경 소유자와 의도를
확인하고, 교육용 표시 컬럼을 되돌릴 때는 다음 DDL을 실행합니다.

```sql
ALTER TABLE [app].[FeatureFlag]
    DROP COLUMN [LabDriftMarker];
```

그 뒤 Plan을 다시 실행해 `deploy.sql`, `deploy-report.xml`,
`deployment-script-policy.md`, `target-databases.json`을 새 artifact로 만들고 새
승인을 받습니다. 새 승인 뒤 비교가 일치하면 예상 exit code는 `0`입니다.

### 강사 노트(수강생이 흔히 하는 오해)

- 승인 상태는 DB를 잠그지 않습니다. 승인과 실행 사이 변경을 별도로 확인해야 합니다.
- shard-aware 비교의 `-CompareOperationsOnly`는 비교 생략이 아닙니다. 서버·DB 이름
  같은 대상별 메타데이터를 제외하고 실제 작업 목록을 비교합니다.
- current report를 approved 위치에 덮어쓰면 감사 근거를 파괴합니다.
- 드리프트가 선한 긴급 수정이어도 기존 승인의 범위를 벗어났으므로 재승인이 필요합니다.
- SQL MI를 사용할 수 없는 강의에서는 사전에 캡처한
  `approved-report.xml`과 `current-after-drift-report.xml`을 오프라인 PC에 복사하고,
  SHA-256을 강사 자료와 대조한 뒤
  `Confirm-DeploymentPlan.ps1 -CompareOperationsOnly`만 실행합니다. 차단 로그와 두 report의 `Operations` 차이를
  함께 화면에 제시하고 실제 배포 성공으로 설명하지 않습니다.

## Lab C — AI blocking finding

> 이 랩은 실제 SQL MI 환경에서 미검증입니다. 강의 전 리허설이 필요합니다.

### 목적

대형 테이블에 기본값 포함 NOT NULL 컬럼과 인덱스를 한 번에 추가하는 SQL을 고정 AI
응답으로 검토합니다. `-FailOnBlockingFindings`가 없으면 finding을 보존한 advisory
성공, 있으면 차단 실패가 되는지 네트워크 없이 검증합니다.

### 사전 조건

- PowerShell 7만 필요하며 Azure 로그인, endpoint, API key는 사용하지 않습니다.
- 입력은 [`risky-change.sql`](../labs/lab-c-ai-blocking/risky-change.sql), 응답은
  [`blocking-review.json`](../labs/lab-c-ai-blocking/blocking-review.json)입니다.
- 실제 모델 응답은 모델·배포·시점에 따라 비결정적입니다. 교육 재현과 자동 테스트의
  판정 기준은 항상 저장소 fixture입니다.

### 재현 절차(명령 포함)

```powershell
New-Item -ItemType Directory -Force ./artifacts/labs | Out-Null

# advisory 모드
pwsh ./eng/Invoke-AiDatabaseReview.ps1 `
  -ReviewInputPath ./labs/lab-c-ai-blocking/risky-change.sql `
  -ValidateOnlyResponsePath ./labs/lab-c-ai-blocking/blocking-review.json `
  -OutputPath ./artifacts/labs/lab-c-advisory.json
# 2026-08-02 실측 exit code: 0
# artifacts: lab-c-advisory.json, lab-c-advisory.md

# blocking 모드
pwsh ./eng/Invoke-AiDatabaseReview.ps1 `
  -ReviewInputPath ./labs/lab-c-ai-blocking/risky-change.sql `
  -ValidateOnlyResponsePath ./labs/lab-c-ai-blocking/blocking-review.json `
  -OutputPath ./artifacts/labs/lab-c-blocking.json `
  -FailOnBlockingFindings
# 2026-08-02 실측 exit code: 1
# artifacts: lab-c-blocking.json, lab-c-blocking.md
```

### 기대 결과(실제 오류 메시지 또는 artifact 발췌)

advisory JSON은 exit code `0`이어도 finding을 삭제하지 않습니다.

```json
{
  "risk": "high",
  "blockingFindings": [
    {
      "file": "labs/lab-c-ai-blocking/risky-change.sql",
      "line": 1
    }
  ]
}
```

blocking 모드는 같은 JSON/Markdown artifact를 쓴 뒤 다음 오류와 non-zero를
반환합니다.

```text
AI review reported 1 blocking finding(s).
```

### 복구 절차

SQL을 nullable 컬럼 추가, 재시작 가능한 배치 backfill, NULL 잔여 검증, NOT NULL
전환, 인덱스 생성 단계로 나눕니다. 각 단계의 잠금·로그·온라인 인덱스 지원 여부를
검증한 뒤 fixture도 새 설계에 맞는 advisory 또는 low-risk 응답으로 갱신합니다.
`-FailOnBlockingFindings`만 제거해 파이프라인을 통과시키지 않습니다.

### 강사 노트(수강생이 흔히 하는 오해)

- advisory 성공은 AI가 승인했다는 뜻이 아니라 사람이 검토할 artifact를 생성했다는
  뜻입니다.
- validation mode는 네트워크를 호출하지 않으며 실제 AI 품질을 측정하지 않습니다.
- AI finding은 보조 신호입니다. DacFx, SQL 정책, 승인, 통합 테스트를 대체하지 않습니다.
- 실제 AI 응답의 문장 일치를 테스트하면 비결정적 회귀가 되므로 fixture 계약을
  테스트합니다.

## Lab D — deploy.sql 파괴 DDL gate

### 목적

필수 샘플 [`destructive-deploy.sql`](../labs/samples/destructive-deploy.sql)의
`DROP TABLE`을 Phase 1
[`Test-DeploymentScript.ps1`](../eng/Test-DeploymentScript.ps1)이 `DEPLOY001`
error로 차단하는지 확인합니다. 활성 예외는 통과하고 같은 예외가 만료되면 다시
실패하는 수명주기도 확인합니다.

### 사전 조건

- PowerShell 7만 필요하며 DB와 네트워크는 필요하지 않습니다.
- 활성 fixture의 교육용 ticket은 `TRAINING-PHASE4-LABD-001`, 명시적 미래 만료일은
  `2099-12-31`입니다.
- allowlist는 실제 운영 승인, 변경 심의, 백업, 복구 계획을 대체하지 않습니다.

### 재현 절차(명령 포함)

```powershell
New-Item -ItemType Directory -Force ./artifacts/labs | Out-Null

# 기본 차단
pwsh ./eng/Test-DeploymentScript.ps1 `
  -ScriptPath ./labs/samples/destructive-deploy.sql `
  -ReportPath ./artifacts/labs/lab-d-blocked.md
# 2026-08-02 실측 exit code: 1

# 미래 만료일의 교육용 allowlist
pwsh ./eng/Test-DeploymentScript.ps1 `
  -ScriptPath ./labs/samples/destructive-deploy.sql `
  -AllowlistPath ./labs/lab-d-destructive-gate/allowlist-active.json `
  -ReportPath ./artifacts/labs/lab-d-allowed.md
# 2026-08-02 실측 exit code: 0

# 만료된 같은 예외
pwsh ./eng/Test-DeploymentScript.ps1 `
  -ScriptPath ./labs/samples/destructive-deploy.sql `
  -AllowlistPath ./labs/lab-d-destructive-gate/allowlist-expired.json `
  -ReportPath ./artifacts/labs/lab-d-expired.md
# 2026-08-02 실측 exit code: 1
```

두 allowlist fixture 모두 `{ rule, pattern, ticket, expiresOn }` 네 속성을 포함합니다.

### 기대 결과(실제 오류 메시지 또는 artifact 발췌)

2026-08-02 실측 결과는 기본 `1`, 활성 allowlist `0`, 만료 allowlist `1`입니다.
기본 및 만료 fixture의 핵심 오류는 다음과 같습니다.

```text
Deployment script policy failed with 1 error(s).
```

`artifacts/labs/lab-d-blocked.md`에는 다음 행이 포함됩니다.

```text
| active | error | DEPLOY001 | 1 | `DROP TABLE [dbo].[Phase4LabD];` |
```

활성 fixture의 `artifacts/labs/lab-d-allowed.md`는 `Errors: 0`,
`Allowlisted findings: 1`, `allowlisted: TRAINING-PHASE4-LABD-001 (expires
2099-12-31)`을 기록합니다. 만료 fixture의 report에는 `Expired allowlist entries`
섹션이 생기고 finding이 다시 active error가 됩니다.

### 복구 절차

가장 안전한 복구는 파괴 DDL을 제거하고 expand/migrate/contract로 다시 설계하는
것입니다. 정말 필요한 교육 예외라면 rule과 대상 statement를 좁게 매칭하고, 교육용
ticket과 짧은 만료일을 기록하고, 별도 승인 후 사용합니다. 만료 후에는 예외 연장보다
변경이 아직 필요한지 먼저 재검토합니다. 운영에서는 allowlist 통과와 별개로 조직의
변경 승인과 복구 가능성 검증을 완료해야 합니다.

### 강사 노트(수강생이 흔히 하는 오해)

- allowlist는 rule 전체를 끄는 스위치가 아니라 특정 statement의 임시 예외입니다.
- `2099-12-31`은 시간에 흔들리지 않는 교육 fixture용 날짜이며 운영 예외의 모범
  만료일이 아닙니다.
- warning이 없는 것은 안전 승인과 같지 않습니다.
- 정규식 기반 교육 gate이므로 주석이나 문자열의 문구를 오탐할 수 있습니다. report를
  사람이 검토해야 합니다.

## Lab E — CommandTimeout(선택)

### 목적

대량 행 적재와 인덱스 생성이 클라이언트의 60초 command timeout을 넘을 수 있다는
개념을 선택적으로 관찰합니다. 이 랩은 안전 게이트의 결정적 회귀가 아니며 하드웨어,
Docker 자원, 캐시, 스토리지에 따라 성공하거나 timeout이 날 수 있습니다.

### 사전 조건

- 폐기 가능한 로컬 SQL Server 컨테이너와 `sqlcmd`가 필요합니다.
- 최소 수 GB의 여유 디스크와 메모리를 확인합니다.
- 운영/공유 DB에서는 절대 실행하지 않습니다.
- Lab A 컨테이너는 자동 삭제되므로 Lab E에는 별도 교육 컨테이너를 준비합니다.

### 재현 절차(명령 포함)

```powershell
sqlcmd -S 'localhost,14334' -U sa -P $labPassword -C `
  -d Phase4TimeoutLab -b -t 60 `
  -i ./labs/lab-e-command-timeout/large-index-workload.sql `
  -o ./artifacts/labs/lab-e-timeout.log
# 실측 환경에 따라 0 또는 non-zero(비결정)
# artifact: artifacts/labs/lab-e-timeout.log
```

fixture는 1,000,000행을 적재하고 include 컬럼이 있는 인덱스를 만듭니다. timeout을
강제로 만들기 위한 `WAITFOR`나 무리한 행 수 증가는 사용하지 않습니다.

### 기대 결과(실제 오류 메시지 또는 artifact 발췌)

2026-08-02 Windows Docker Desktop의 SQL Server 2025 컨테이너에서 `-t 60`으로
실행한 실측값은 exit code `0`, 경과 시간 `8.86초`, timeout `false`였습니다.
명령이 별도 메시지를 출력하지 않아 핵심 error text도 없었습니다. 이 하드웨어에서는
60초 timeout을 안정적으로 재현하지 못했으며, `Query timeout expired`를 실측값처럼
제시하지 않습니다. 결과는 캐시, 스토리지, CPU와 메모리에 따라 비결정적입니다.

### 복구 절차

먼저 세션과 트랜잭션 상태를 확인하고 무조건 재실행하지 않습니다. 작업을 배치화하거나
유지보수 창·온라인 인덱스 지원을 검토한 뒤, 충분한 근거가 있을 때만 이 저장소의 실제
경로에서 제한 시간을 조정합니다.

- publish profile: `pipelines/profiles/sqlmi-dev.publish.xml`,
  `sqlmi-test.publish.xml`, `sqlmi-prod.publish.xml`의 `<CommandTimeout>3600</CommandTimeout>`
- pipeline parameter: `azure-pipelines.yml`의 `sqlCommandTimeout`
- 실행 전달: `pipelines/templates/deploy-stage.yml`의
  `-CommandTimeout ${{ parameters.sqlCommandTimeout }}`

상향 뒤 작업별 예상 시간과 관찰 지표를 기록하고 다시 실행합니다.

### 강사 노트(수강생이 흔히 하는 오해)

- timeout 증가는 성능 문제 해결이 아니라 클라이언트 대기 한도 변경입니다.
- client timeout 뒤 서버 작업이 즉시 끝났다고 가정하지 않습니다.
- 이 저장소 profile은 기본값 의존을 피하려고 3600초를 명시합니다. 60초 실습은
  `sqlcmd -t 60`으로 개념을 재현합니다.
- Lab E는 비결정적이므로 `eng/Test-FailureLabs.ps1`의 필수 통과 조건에 포함하지
  않습니다.
