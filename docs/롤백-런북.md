# SQL MI 배포 롤백 런북

이 문서는 DACPAC 카나리/샤드 배포가 실패했을 때 데이터 손실을 늘리지 않고 복구 방향을
결정하기 위한 운영 절차입니다. 기본 원칙은 **먼저 배포를 멈추고, 증거를 보존하고,
되돌릴 수 있는 변경만 롤백하며, 그 외에는 forward-fix** 하는 것입니다.

## 1. 배포 전 준비와 PITR 기준시각

`Deploy*` stage는 실제 SqlPackage 실행 직전에 UTC 시각을
`deployment-review-<environment>-pitr-marker` artifact의 `pitr-marker.json`에 기록합니다.
파일에는 환경, 서버, 전체 대상 DB, build ID, source commit이 포함됩니다. 이 시각은
복원 작업의 기준점이지 백업 완료 증명은 아닙니다. 승인자는 다음을 먼저 확인합니다.
marker publish는 cancellation에서도 `always()`로 평가되며, capture가 성공해 파일이 있을
때만 게시하므로 부분 배포의 기준시각을 보존하고 원래 실패를 게시 오류로 가리지 않습니다.

1. SQL MI 자동 백업 보존 기간에 예정 작업과 복구 판단 시간이 포함되는지 확인합니다.
2. 장기 보존, 규제 또는 대규모 비가역 변경이면 별도 COPY_ONLY 백업을 완료하고
   `RESTORE VERIFYONLY` 결과와 Blob immutable/retention 정책을 변경 티켓에 첨부합니다.
3. 카나리 DB가 목록의 첫 번째 DB이며 업무 대표성이 있는지 확인합니다.
4. `deploy.sql`, `deploy-report.xml`, 정책 보고서와 전수 계획 검사 결과를 확인합니다.

PITR은 원본을 제자리에서 되감는 작업으로 취급하지 않습니다. 기준시각 직전으로 **새
데이터베이스를 복원**하고 애플리케이션 연결 전환 또는 검증된 데이터 병합 절차를 사용합니다.

## 2. SQL MI COPY_ONLY URL 백업

자동 PITR만으로 RTO/RPO 또는 감사 요건을 충족하지 못하거나, 대형 테이블 재작성·데이터
정리처럼 되돌리기 어려운 변경 전에는 SQL MI native backup을 Azure Blob URL로 만듭니다.
스토리지 방화벽/네트워크, 용량, SAS 만료, SQL MI 권한과 암호화 정책을 먼저 검증합니다.
SAS는 Key Vault 등 승인된 비밀 저장소에서 주입하며 스크립트나 로그에 기록하지 않습니다.

```sql
USE [master];
GO

-- 컨테이너 범위 credential은 사전에 DBA가 만들고 SAS 비밀을 안전하게 주입한다.
CREATE CREDENTIAL [https://<storage-account>.blob.core.windows.net/<container>]
WITH IDENTITY = 'SHARED ACCESS SIGNATURE',
     SECRET = '<sas-token-without-leading-question-mark>';
GO

BACKUP DATABASE [<database-name>]
TO URL = 'https://<storage-account>.blob.core.windows.net/<container>/<database>-predeploy-<utc>.bak'
WITH COPY_ONLY, COMPRESSION, CHECKSUM, STATS = 5;
GO

RESTORE VERIFYONLY
FROM URL = 'https://<storage-account>.blob.core.windows.net/<container>/<database>-predeploy-<utc>.bak'
WITH CHECKSUM;
GO
```

`COPY_ONLY`는 정규 backup/differential 체인의 기준을 변경하지 않습니다. 완료 메시지만으로
복구 가능하다고 판단하지 말고 `RESTORE VERIFYONLY`, Blob 크기, 보존 잠금과 별도
데이터베이스 restore rehearsal을 확인합니다. 백업 생성 시간이 배포 창을 초과하면 배포를
연기하며, 검증되지 않은 백업을 근거로 승인하지 않습니다.

## 3. 복구 결정

| 상태 | 즉시 조치 | 복구 방향 |
|---|---|---|
| 배포 명령 timeout, 성공 여부 불명 | 후속 샤드 시작 금지, SQL MI 작업/잠금 확인과 DeployReport 재생성 | 현재 계획을 승인본과 다시 비교한 뒤 같은 immutable DACPAC 재시도 |
| 카나리 실패 | 나머지는 실행기가 자동 중지, 로그·현재 스키마·PITR marker 보존 | 원인 수정 후 새 계획/승인 또는 카나리 PITR/forward-fix |
| 일부 샤드 성공 | 실패 DB 목록과 성공 요약 보존, 애플리케이션 호환성 확인 | 같은 DACPAC으로 파이프라인 재실행. 성공한 DB는 no-op이 되고 실패한 DB에만 변경이 적용됨 |
| 배포 성공, smoke 실패 | 트래픽 확대 중지, 데이터/프로시저 동작과 앱 호환성 확인 | 스키마가 안전하면 테스트/데이터 forward-fix, 비호환이면 연결 전환 또는 검증된 복원 |
| 승인 후 drift | 배포하지 않음 | 수동 변경 원인 제거 또는 소스 반영 후 Plan과 승인을 새로 생성 |
| 토큰 만료로 후반 샤드 인증 실패 | 진행 중인 fan-out 중단, 성공/실패 DB 목록 확보 | 대상을 나누어 새 pipeline run으로 재시도 |
| 파괴/비가역 변경 | 쓰기 트래픽 중지, 증거 및 백업 보존 | 원칙적으로 forward-fix; 데이터가 손실되었고 RPO 승인을 받았을 때만 PITR/백업 복원 |

재시도에는 같은 build의 immutable DACPAC과 동일 publish profile을 사용합니다. 배포 직전
각 DB의 DeployReport를 같은 profile로 다시 생성해 승인본과 비교하며, 다르면 실행하지
않고 새 Plan과 승인을 요구합니다.

`Deploy-Databases.ps1`은 DeployReport에 schema operation이 없어도 배포를 건너뛰지
않습니다. post-deployment data 작업은 DeployReport에 나타나지 않으므로, 보고서가
비어 있다는 사실을 "이미 최신"의 근거로 사용하지 않습니다. 완전한 no-op에도 연결·실행
비용이 발생하지만 data-only 배포 누락을 방지합니다.

이 성질 덕분에 부분 성공 상태의 재시도는 단순합니다. 성공한 DB는 스키마 변경이 없으므로
사실상 no-op으로 지나가고, 실패한 DB에만 실제 변경이 적용됩니다. 별도의 부분 복구 경로를
두지 않습니다.

`deploymentMode=ValidatedScript`인 경우에는 DeployReport 비교에 더해 생성된 Script
원문이 승인본과 일치해야 합니다. 다중 DB rollout에서는 `validateAllDatabasePlans=true`가
필수이며, 그렇지 않으면 실행 전에 차단됩니다.

Azure SQL access token은 fan-out 시작 직전에 한 번 발급해 모든 대상 DB에 재사용하며
롤아웃 중 갱신하지 않습니다. 토큰 수명은 대략 60~90분이므로 대상이 많거나 DDL이 길면
후반 샤드에서 인증 오류가 발생할 수 있습니다. 이 경우 스키마 문제나 권한 문제가 아니라
토큰 만료를 먼저 의심하고, 대상을 나누어 새 pipeline run으로 재시도합니다.
배포 시작 시 JWT `exp`를 확인해 기본 최소 잔여 수명 20분보다 짧으면 SqlPackage 호출 전에
중단하며, `exp`를 해석할 수 없는 토큰은 경고 후 기존 절차대로 진행합니다.

## 4. 되돌릴 수 없는 변경과 forward-fix

컬럼/테이블 삭제, 타입 축소, 데이터 정리, 암호화 키·로그인 변경, 외부 시스템에 이미
소비된 식별자 변경은 단순 역방향 DDL로 원상복구되지 않습니다. 이전 DACPAC 게시도 삭제된
행이나 변환 전 값을 복원하지 못합니다. 이러한 변경은 expand → migrate → contract로
분리하고, contract 전 호환 기간과 검증된 백업을 둡니다.

운영 기본 선택은 새 immutable DACPAC 또는 승인된 데이터 보정 스크립트로 목표 상태를
회복하는 forward-fix입니다. PITR/restore는 허용된 데이터 손실 범위, 복원 소요 시간,
현재 쓰기와의 병합 방법, 연결 전환 및 되돌리기 계획을 사고 지휘자가 승인했을 때만 수행합니다.

## 5. 복구 후 확인

1. 복원 또는 forward-fix DB에서 `eng/Test-DeployedDatabase.ps1`과 애플리케이션 핵심
   트랜잭션을 실행합니다.
2. 모든 샤드의 스키마/데이터 버전, 실패 목록, 연결 문자열 전환 상태를 대조합니다.
3. SQL MI 감사 로그, Pipeline run, deployment-review artifact, PITR marker, backup URI,
   변경/사고 티켓을 상호 연결합니다.
4. 수동 DDL이 있었다면 소스에 반영하고 새 DeployReport와 승인을 생성합니다.

## 6. BACPAC을 일반 롤백에 사용하지 않는 이유

BACPAC은 논리적 스키마/데이터 이동과 테스트 환경 시딩 도구입니다. 온라인 export의
트랜잭션 일관성, 대용량 처리 시간, SQL Agent job/login 같은 인스턴스 오브젝트, 서버 설정,
일부 권한과 운영 메타데이터를 완전한 시점 복구 형태로 보장하지 않습니다. 따라서 일반
운영 롤백에는 PITR 또는 검증된 native COPY_ONLY backup을 사용하고, BACPAC은 별도
일관성 검증을 거친 마이그레이션/시딩에만 사용합니다.
